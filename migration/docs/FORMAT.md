# CipherSetu envelope v1

This is an application-specific JSON envelope, not OpenPGP, CMS, or a universal backup format.
All binary fields use standard padded base64 through Go encoding/json. Max plaintext:
16 MiB; max encoded envelope: 24 MiB; max key file: 16 KiB. Parser nesting limit: 16.

Fields: header {format="CipherSetu", version=1, id=16 random bytes,
cipher="AES-256-GCM"}, nonce (12 bytes), ciphertext (plaintext + 16-byte tag),
suite, recipient (64 lowercase hex SHA-256 characters generated by the application),
wrapped_key.

Data AAD is compact Go JSON of Header in declared field order. Key wrapping context
is compact Go JSON of the struct in `Envelope.context()`, with field names and order
`Domain`, `Header`, `Nonce`, `PayloadHash`, `Suite`, `Recipient`. Domain is
`CipherSetu/key-wrap/v1`; PayloadHash is lowercase SHA-256 hex of ciphertext.
This ordering is part of v1; other implementations must reproduce it exactly.
The input JSON envelope may be pretty-printed or reordered; contexts are regenerated
from typed fields rather than raw input bytes. No filenames, dates, or plaintext hashes
are stored in envelopes.

Legacy suite: RSA-3072-OAEP-SHA256, exponent 65537. OAEP label is wrapping context;
wrapped_key is 384 bytes. This format is only a controlled migration source.

Destination suite: HPKE-MLKEM768-X25519-HKDFSHA256-AES256GCM. Uses
`crypto/hpke.MLKEM768X25519()` (X-Wing), `HKDFSHA256()`, `AES256GCM()`.
Go hpke.Seal serializes encapsulation || ciphertext; wrapping context is HPKE info.
Wrapped plaintext is exactly the 32-byte AES data key. WrappedKey is 1168 bytes
(1120-byte encapsulation + 32-byte encrypted DEK + 16-byte tag). No manual KEM combiner,
HKDF schedule, or HPKE nonce construction is implemented by this project.

Keys: {version:1, suite, kind:"public"|"private", material:base64}.
RSA material uses PKIX public / PKCS8 private DER. HPKE material uses Go KEM
PublicKey.Bytes / PrivateKey.Bytes serialization. Private material is unencrypted.
Recipient ID = SHA256(compact JSON of canonical public Key in declared struct order).

Changing primitive choices or serialization requires a new explicit supported format;
unknown versions and suites fail closed. Standards implemented underneath are not a
claim that this application-specific format is independently reviewed.
